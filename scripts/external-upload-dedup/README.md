# Offline-план существующих External / Managed пар

`plan.mjs` проверяет **предоставленный снимок аудита**, а не production. Он читает
только JSON, не подключается к PostgreSQL/Redis/NAS, не читает оригиналы и не
содержит режима применения, SQL DELETE, перемещения или удаления файлов.

```bash
node scripts/external-upload-dedup/plan.mjs audit.json > review-plan.json
node --test scripts/external-upload-dedup/plan.test.mjs
```

Допускается JSON через stdin (`plan.mjs -`). Коды завершения: `0` — план требует
ручной проверки, `2` — блокирующие несоответствия, `1` — ошибка ввода. Даже код `0`
означает `REVIEW_REQUIRED`, а не разрешение объединять объекты.

Снимок содержит `version: 1`, один `ownerId`, явную `allowlist` пар
`{externalId, managedId}`, массив `pairs` и словарь полных исходных `records`.
Каждая пара включает:

- `external` и `managed`: настоящие UUID/owner/library, пути, active/online-состояние,
  читаемость библиотеки и свежие доказательства одинаковых SHA-256/размера обычных
  стабильных файлов, без symlink. Доказательства старше 15 минут отклоняются.
- `inventory`: UUID обоих объектов, fingerprint схемы, фактический список
  зависимостей каталога и проверенные решения по всем областям из `SCOPES`.
  Неизвестная таблица, непроверенная связь или конфликт блокирует план.
- Для переносимых связей — ссылки на полные исходные строки в `records`, решение
  reviewer и UUID сохраняемого External. Для дедупликации связей нужны также
  полные строки назначения. Исходные записи остаются неизменными.

Синтетический пример построения структуры находится в `plan.test.mjs`. Данные
реального аудита и пользовательские metadata не следует коммитить или передавать
в Cloud. JSON может содержать личные сведения; хранить его локально у владельца.

Планировщик проверяет форму и внутреннюю согласованность доказательств. Он не
может удостоверить правдивость `complete`, полноту отсутствующих в JSON FK,
фактические байты NAS, подпись доказательств или сохранность связей после будущего
применения. Это остаётся предметом read-only аудита и ручной проверки. Успешный
план не заменяет реализацию и integration/crash-recovery тесты будущего merger.

Результат сохраняет External UUID/path, перечисляет предлагаемые remaps через
ссылки на исходные записи и описывает отдельные будущие этапы: согласование,
durable journal и атомарное сохранение связей, проверка survivor/sync, затем
отдельно согласованный карантин Managed-only оригинала. Автоматического apply
нет. Шесть реальных пар этим инструментом не изменяются.

Полный аудит зависимостей, read-only команды HP, ограничения обычного Duplicate
Resolve и проект отката: [документ remediation](../../specs/2026-10-26-external-upload-dedup-remediation-design.md).
