# Бесплатная iOS-дистрибуция «Фото»: техническое заключение

Дата исследования: **5 октября 2026 года**. Это отдельный архитектурный отчёт, а не внедрение. Конфигурация HP, приложение, идентификаторы, подпись, workflow и production не изменены. Реализация схемы требует подтверждения владельца и физического испытания на целевом iPhone.

## Вывод и предлагаемая схема

Для актуального обычного iPhone не найдено подтверждённого бесплатного способа гарантировать одновременно бессрочную работу нашего собственного IPA, полностью невидимое продление подписи, отсутствие повторного обращения к компьютеру даже при отказах и сохранение всех capabilities. Бесплатная Personal Team оставляет эффективный срок установленного приложения около семи дней. Автоматический refresh снижает повседневные действия, но не отменяет срок и зависимость от Apple, разрешений iOS, pairing и фонового выполнения.

Предлагается **пилот SideStore + LocalDevVPN + ежедневная Personal Automation «Refresh All Apps»**, с обычным самостоятельным IPA «Фото» и контролируемым HTTPS-источником обновлений. Сначала проверяется on-device Anisette; собственный Anisette v3 на HP является дополнительным вариантом, если он действительно нужен проверенной версии. В приложении не будет зависимости от SideStore API. Установка сервисов на HP до подтверждения этой архитектуры не предусмотрена.

Сейчас этот вариант нельзя назвать production-ready. Официальный [SideStore 0.6.4](https://github.com/SideStore/SideStore/releases/tag/0.6.4), выпущенный 9 сентября 2026 года, явно помечен **«DO NOT USE — SIGN-IN IS BROKEN ON 0.6.4 AND BEFORE»**. [0.7.0-alpha](https://github.com/SideStore/SideStore/releases/tag/0.7.0-alpha) от 11 сентября — временное исправление sign-in/503 после изменений Apple. Релиз использует commit `6032424a0e56c1c319762e786099bdd9186a238b` и версию `0.7.0-20260911.328+6032424a`. Он годится как зафиксированный кандидат для испытания, а не как обещание стабильности. Перед реальной установкой надо повторно проверить официальные release notes и выбрать исправленный стабильный выпуск, если он появился. Nightly автоматически не обновлять.

Есть два отдельные технические условия допуска: возможность сохранить требуемый фактический bundle ID при Personal Team и согласованность App Group entitlement с собственным ключом `AppGroupId`. Ни одно из них нельзя объявить выполненным по одному README SideStore.

### Bundle ID и App Groups — обязательная проверка до установки

SideStore по умолчанию использует `appendTeamID=true`. В проверенном 0.7.0-alpha его provisioning operation формирует `<original-bundle-id>.<TeamID>`; App Groups также получают Team suffix. Следовательно, «не меняли bundle ID в Git» не означает «на iPhone установлен прежний bundle ID».

Исходные bundle IDs в обычной конфигурации и unsigned IPA сохраняются. Для позднее подготовленного отдельного бесплатного pilot используется `prepare_sidestore.py` и **Append Team ID включён**: seed согласует custom `AppGroupId` и ShareMedia URL scheme с этим поведением signer (точные команды в `docs/RELEASE_RUNBOOK.md`). Это персонализация отдельного артефакта, не изменение обычных target IDs. На iPhone необходимо проверить фактические bundle IDs/профили и затем сохранять те же Team ID, append-настройку и App Group при refresh/update. Успешное free provisioning не гарантировано до физической проверки; переключение signer-настроек может создать отдельную установку и лишить её доступа к прежним данным.

App Groups важны для основного приложения: `URLSessionManager.swift` получает группу из собственного Info.plist-ключа `AppGroupId`, использует shared preferences и authenticated cookies. Widget и Share используют ту же группу. В [ResignAppOperation 0.7.0-alpha](https://github.com/SideStore/SideStore/blob/6032424a0e56c1c319762e786099bdd9186a238b/SideStore/Core/Operations/PipelineOperations/ResignAppOperation.swift) есть исправление `CFBundleIdentifier`, `BGTaskSchedulerPermittedIdentifiers` и `NSExtensionFileProviderDocumentGroup`; общего исправления произвольного `AppGroupId` нет. Поэтому возможен установленный IPA, в котором entitlement разрешает одну группу, а приложение читает другую.

Допуск требует сравнить `AppGroupId` **в каждом из трёх Info.plist** с `com.apple.security.application-groups` каждого подписанного binary и embedded profile. Любая персонализация signed artifact должна быть изолирована в процессе подписи, одобрена отдельно и сохраняться при каждом refresh/update. Не следует добавлять зависимость основного приложения от SideStore или менять общий upstream код ради одного signer.

SideSign, используемый текущим SideStore, включает App Groups в собственный список free features, но не Associated Domains/Wi-Fi Info/APNs. Это свидетельство реализации signer, **не гарантия выдачи Apple профиля**. Нужны фактические profile entitlements и runtime-проверка. При отсутствии Wi-Fi Info отдельно проверить выбор сети/SSID и Wi-Fi-only upload; при отсутствии Associated Domains проверить deep links. PhotoKit, обычный network access, локальные уведомления и background modes не должны без причины удаляться из IPA.

## Жизненный цикл предлагаемого пилота

### Первоначальная настройка

1. На macOS/Xcode собирается обычный Release IPA из проверенного `work`, с существующим branded bundle ID и всеми необходимыми extensions. Ubuntu HP способен хранить/обслуживать IPA и работать с pairing/signing tools, но **не заменяет macOS/Xcode для Flutter iOS native build**. Текущий paid CI не использовать как якобы бесплатный.
2. Владелец проверяет binary/entitlements/profile до передачи IPA. iOS Release Flutter AOT не требует JIT; SideJITServer/StikDebug для «Фото» не нужны.
3. Для установки SideStore подключают iPhone кабелем к доверенному компьютеру один раз. Официальный iloader поддерживает macOS/Windows/Linux; на Ubuntu нужен `usbmuxd`. Это может быть HP с доступным USB и подходящим desktop/remote desktop, а не обязательно Mac. Mac остаётся нужен для создания нового IPA, не для каждого refresh.
4. На iPhone устанавливают LocalDevVPN из официального источника, разрешают VPN configuration; доверяют development profile. iOS 16+ требует Developer Mode и перезагрузку. На iOS 18+ официальный guide также указывает Allow & Restart при доверии profile.
5. Вводят Apple Account/2FA в доверенном signing client, устанавливают SideStore и pairing; после установки **сначала refresh самого SideStore**, затем нашего IPA. Пароли, pairing keys, `adi.pb`, certificate/private key и `.sideconf` не публикуют и не кладут в Git.
6. Добавляют свой HTTPS source, проверяют установку «Фото», login/PhotoKit/background. Включают SideStore Background Refresh и локальные уведомления об expiry/failure.
7. В Shortcuts создают ежедневную Personal Automation в момент ожидаемой доступности Wi-Fi/зарядки с «Refresh All Apps», с автоматическим запуском без обычного подтверждения, если конкретная iOS позволяет. LocalDevVPN должен быть активен при refresh. Испытывают также резервный trigger при подключении питания. Shortcut исполняется **на телефоне**; cron HP не может заставить iOS гарантированно запуститься.

«Компьютер только один раз» — нормальный успешный сценарий, **не гарантия на весь срок эксплуатации**. Официальная pairing guide прямо предупреждает о возможной invalidation после update/reset и даже непредвиденно; для восстановления может снова потребоваться компьютер/USB.

### Продление, сбои и срок восстановления

Refresh переподписывает и переустанавливает тот же app bundle с новым provisioning profile. При стабильных Team/ID/group сохраняется app data; обычное продление не должно требовать удаления IPA и не должно скачивать новое обновление приложения. Это нужно подтвердить на нашем IPA, включая logout/Keychain/database/widgets после двух полных seven-day циклов.

SideStore пытается выполнять refresh в фоне; iOS может не дать времени, Low Power Mode/отключённый Background App Refresh/force-quit/недоступный Wi-Fi/VPN/2FA/Apple outage способны сорвать попытку. В 0.7.0-alpha `RefreshAllAppsIntent` после примерно **27 секунд** может запросить продолжение в foreground. У обычного пользователя тогда возможен видимый запрос. Background refresh не имеет SLA и не даёт права скрыть сообщения об ошибке.

Время восстановления равно **остатку до фактического `ExpirationDate` установленного профиля**, а не ещё семи дням после каждой неудачной попытки. При ежедневном успешном refresh обычно есть несколько дней запаса. Практическая цель — уведомлять владельца при отсутствии успеха сутки и эскалировать при остатке ≤48 часов. Это предлагаемая эксплуатационная политика, не уже внедрённый HP мониторинг. HP видит здоровье Anisette/HTTPS, но без дополнительного отдельно согласованного механизма не знает, действительно ли конкретный iPhone переподписал «Фото».

Если истекло «Фото», но SideStore ещё работает, попробовать переустановку того же IPA/обновление тем же signer **без удаления приложения**. Если истёк SideStore, автоматизация не может запустить истёкший binary: потребуется повторная установка через доверенный компьютер. Отдельного гарантированного grace period после expiry нет. Нельзя обещать отсутствие ручного восстановления.

| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## HP Ubuntu 24.04 и Anisette v3

HP нужен для своего HTTPS IPA/source хостинга и, при выборе remote режима, для отдельного Anisette v3. Immich/Gallery server, Magic Eraser, AI Memories, PostgreSQL/Redis/ML не меняются. Новый signing-related service не включать в основной Compose до отдельного решения.

Проверенный [Dadoum/anisette-v3-server](https://github.com/Dadoum/anisette-v3-server/tree/684895737aaf1a1c4586fcd5b67509ffd500a36c) поддерживает Linux amd64/Docker и оба v1/v3 протокола. Dockerfile запускается непривилегированным пользователем `Alcoholic`, слушает **6969**, содержит постоянный cache библиотек в `/home/Alcoholic/.config/anisette-v3/lib/`. Простой upstream пример публикует порт на всех интерфейсах; **его нельзя копировать в production без изоляции**. В проверенном HTTP router нет обязательной client authentication.

Для будущего внедрения нужен отдельный Compose project с закреплённым source commit/image digest, `restart: unless-stopped`, ограничениями RAM/CPU/PIDs, без privileged/host networking/Docker socket/gallery storage и с приватным постоянным volume. Начальные небольшие лимиты определяются smoke/load test, а не выдуманным измерением: нагрузка Anisette намного меньше inpainting, но в этой среде сервис не запускался и точные RAM/latency неизвестны. Read-only root FS допустим только после проверки всех runtime/cache write paths.

Порт 6969 не публикуют в Интернет. Для домашнего пилота достаточно доверенной LAN/доступного iPhone внутреннего HTTPS reverse proxy; remote сценарий требует отдельной аутентификации и поддержки WebSocket `/v3/provisioning_session`. Нельзя включать Basic Auth/mTLS и считать работу SideStore подтверждённой: в проверенной конфигурации клиента нет готовой произвольной Authorization-настройки, поэтому совместимость должна пройти испытание. Имена/UUID в URL не считаются полноценной защитой. IP allowlist/rate limits полезны, но не превращают публичный открытый signing-helper в приватный сервис.

Не планировать одновременно Tailscale/WireGuard remote access и LocalDevVPN как заведомо совместимые: обычные iOS VPN tunnels могут конфликтовать. Доступность HP во время local VPN проверяется отдельно; до этого удалённый own-v3 сценарий не объявляется готовым. Дома можно начать с LAN HTTPS и on-device Anisette, не публикуя сервис.

Anisette сервер не должен получать Apple password/2FA/signing private key или фото. В v3 он, однако, обрабатывает device/provisioning information и `adi_pb`; это чувствительное состояние, не «сервер вообще не видит никаких данных». Volume/backups/logs ограничивают, provisioning/header содержимое не печатают. Документация SideStore говорит, что account credentials в Anisette не отправляются; пароль при первоначальной установке также вводится в iloader, а не магически всегда остаётся только на телефоне.

Нужно учесть лицензии: open-source Anisette server при запуске загружает из Apple Music APK библиотеки Apple (`libCoreADI.so`, `libstoreservicescore.so`). Это не даёт права произвольно распространять их в нашем публичном image. Предпочтительно local cache при первом запуске согласно upstream; условия Apple и собственный account policy проверяются владельцем отдельно.

В нынешнем SideStore on-device Anisette включён по умолчанию, но использует `remoteODA` metadata source/fallback (`https://zzz.haus/oda.json`) и загружаемые данные/библиотеки. Это **не полностью offline и не полностью self-hosted signing**. Удаление этой зависимости потребует отдельного исследования происхождения/проверки assets и возможностей конкретного signer. Ни телефонные оригиналы, ни Gallery token для этого не требуются. Apple provisioning endpoints неизбежно остаются внешними.

## Обновления IPA и видимые компоненты

В собственном HTTPS AltSource хранится обычный IPA и metadata `bundleIdentifier`, `version`, `buildVersion`, `downloadURL`, `size`, `minOSVersion`, description/icon. URL версий неизменяемые; IPA публикуется целиком до atomic switch source JSON. Сохраняются предыдущий проверенный IPA и SHA-256 manifest владельца; нельзя считать, что любой source client автоматически проверяет наш дополнительный SHA field. Никаких credentials, Gallery session token или личных фото в source нет. Source в обычном формате, без marketplace/notarization полей для неподписанного Personal Team IPA.

После добавления source SideStore показывает новое обновление; пользователь нажимает Update, получает обычную установку поверх предыдущей без ручного удаления. **Refresh All Apps продлевает установленную версию и не равен автоматической установке новой версии**. Проверенные docs явно предлагают нажать Update, а код fetchSources показывает notification. Полностью unattended app update не подтверждён.

В 0.7.0-alpha существует `Install IPA` App Intent. Отдельная Shortcut, которая получает версию/IPA с нашего HTTPS и вызывает его, технически может быть исследована позднее, но это не готовый доверенный update pipeline: нужны validation/download size/integrity/anti-downgrade/error handling, сохранение custom signing settings и проверка foreground timeout. До испытания остаётся один понятный Update в SideStore. К самому «Фото» эта логика не добавляется.

Повседневно пользователь открывает иконку **«Фото»**. SideStore и LocalDevVPN можно убрать с Home Screen в App Library, а Shortcut настроить один раз. Удалять их нельзя. VPN configuration/indicator, Developer Mode, SideStore в Settings/App Library, automation и сообщения failure/expiry могут оставаться видимыми. Делать их полностью невидимыми через частные API/MDM/exploits не предлагается. LocalDevVPN в официальном сценарии устанавливается из App Store или доступного альтернативного marketplace: само «Фото» распространяется вне App Store, но абсолютно нулевое использование App Store для всех вспомогательных компонентов не обещается.

## Физические критерии допуска

Пилот выполняется после подтверждения архитектуры, на одном тестовом iPhone с резервными копиями. Нужны минимум **14 дней**, чтобы пройти два цикла подписи; краткая установка не подтверждает бесшовность.

| Проверка                     | Критерий                                                                                                                                                                                                  |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Signing identity             | Фактический требуемый bundle ID, стабильная Team, три согласованных AppGroupId/entitlements/profiles; корректные expiry/permissions                                                                       |
| Лимиты Personal Team         | До трёх одновременно активных apps, включая SideStore; максимум десять активных App IDs. Main/Share/Widget — отдельные IDs, SideStore/extensions также учитываются; проверить реальные остатки в аккаунте |
| Основной UX                  | «Фото» открывается из Home Screen; login сохраняется после refresh/update/reboot; server-only просмотр и Magic Eraser работают                                                                            |
| Фото и видео                 | PhotoKit limited/full access, чтение/Save to Photos, исходная ориентация/EXIF, Live Photo pair, Share extension и системный Share                                                                         |
| Background                   | Реальные photo/video uploads на Wi-Fi, lock/reboot/SSID restriction, BGTaskScheduler, background URLSession cookies, уведомления                                                                          |
| Extensions                   | Share из других apps, Widget с авторизованным thumbnail; данные не теряются при re-sign                                                                                                                   |
| Automation                   | Daily refresh обоих apps без обязательного подтверждения на конкретной iOS; locked/charging/Low Power/background refresh off/force-quit cases документированы                                             |
| Нативные signing ограничения | Associated Domains/Wi-Fi Info отсутствие не скрыто; нет незаконно удалённых entitlements, crash или потери функций                                                                                        |
| Отказы                       | HP offline 24–48h, Apple/network failure, VPN conflict, pairing replacement, expiry recovery без удаления app data, проверка notification                                                                 |
| Обновление                   | Новой IPA поверх той же identity; source offline/неполный download/неверный version не приводит к потере существующего приложения                                                                         |
| Ресурсы/изоляция HP          | Закреплённый образ, persisted state после restart, auth/WebSocket/network доступ только одобренным клиентам; Gallery/AI контейнеры не пересозданы                                                         |

Если exact bundle ID, App Group, PhotoKit/background или автоматический refresh не проходят, production допуск не даётся. Нельзя обещать цель ценой молчаливого удаления extensions, изменения app identity или неподтверждённых signing bypasses.
