# FOTO Build 29: необратимое принятие очистки корзины

База: `083ff4109ce8cce292176fe08c00c892fe46c1b7` (Build 28).
Ветка: `codex/foto-build29-instant-trash-cleanup`.

Это изменение исходников. APK не собирался, production не изменялся. Реальная
Synology, Samsung, HP и перезагрузка HP из облака не проверялись.

## Почему интерфейс ожидал удаления

Прежний путь `TrashKebabMenu` запускал `BatchDeletionController` и
`AssetService.deleteWithResults()`. API ожидал физического завершения: inline
удаление либо опрос batch/status каждые 250 мс, до 1200 попыток. Модальный
интерфейс оставался открыт, затем дополнительно ожидалось локальное удаление
MediaStore. Доступность NFS и системный диалог Android попадали в длительность
пользовательской операции.

Сам ответ `DELETION_BATCH_QUEUED` не доказывал необратимость: существующий batch
worker создавал per-asset intent позднее. До этого Restore мог выиграть гонку.
Простое скрытие плиток после постановки batch в Redis было бы некорректным.

## Серверный контракт

`POST /assets/permanent-deletion` получает необязательный `acceptOnly: true`.
`confirmed: true`, владелец, текущая корзина и существующая политика удаления
остаются обязательными. Прежний запрос без флага сохраняет прежнюю семантику.

На один запрос (до 5000 UUID) сервер в одной PostgreSQL-транзакции:

1. Берёт существующую блокировку владельца и блокировки выбранных assets.
2. Проверяет владельца, Trash, доступные политики/корни, эксклюзивность оригинала
   и связанных Motion/Live Photo ресурсов. Несанкционированный элемент откатывает
   принятие новых элементов всего запроса.
3. Фиксирует существующие `asset_deletion_tombstone` и переводит assets в
   `Deleted`. Это точка необратимости, до чтения/hash/unlink оригиналов.
4. Публикует логическое удаление в существующий `asset_audit` в той же транзакции.
5. После commit инициирует существующие `AssetDelete` jobs. Redis не входит в
   условие HTTP-подтверждения: потерянный enqueue восстанавливается из PostgreSQL.

Ответ содержит `accepted: true` только при наличии долговременного решения.
`pending` и `failed` при этом не означают физического завершения. `complete`
означает завершение всей операции, включая связанный motion asset. Повторный UUID
использует тот же receipt; повторная доставка jobs безопасна благодаря
идемпотентной обработке и существующим блокировкам.

Restore использует ту же блокировку владельца. Прямой Restore принятого UUID
отклоняется с HTTP 409; Restore All исключает такие объекты. Принятые assets не
входят в пользовательскую корзину. Холодный sync и FK-зависимые записи также
исключаются, а обложка альбома/пространства не ссылается на исключённый asset.
Прежний deprecated AssetsV1 не включается заново.

Новые таблицы, миграции, worker и очередь не добавлены.

## Фоновое удаление и восстановление после сбоя

Используются прежние `AssetDelete` / `AssetDeleteCheck`, политика разрешённых
корней, файловая идентичность, checksum и tombstone. Receipt сохраняется при
частичном отказе; объект остаётся недоступен для восстановления.

Ранее существовал разрыв: удаление asset и `complete` могли предшествовать
постановке отдельного `FileDelete` для превью. Теперь существующий `asset_file`
служит долговременным manifest. Завершающая транзакция заново читает его под
блокировками owner/asset/path, выполняет общий защищённый cleanup производных
файлов, затем удаляет строку asset и фиксирует `complete`. Нельзя удалять путь,
на который ссылается оригинал, Sidecar или файл другого asset/владельца.

Сбой оставляет manifest и `DERIVATIVE_CLEANUP_FAILED`. Повторный проход принимает
`ENOENT` уже удалённого файла как успех и продолжает остальные файлы. Все пути
продолжают проходить существующие проверки disposable-корней и symlink.

При bootstrap microservices запускается существующий `AssetDeleteCheck` с
`resumeOnly: true`: переигрываются только зафиксированные решения, без нового
retention-удаления. Плановый проход и повторный запрос тех же UUID также могут
возобновить их. Активного бесконечного клиентского polling нет. Ошибки видны в
существующих receipt/status API и журнале; они не преобразуются в `complete`.

В настоящем окружении всё равно требуется надёжный PostgreSQL storage и
проверка восстановления backup. Тест с новым экземпляром репозитория не является
испытанием отключения питания HP.

## Android: cache, sync и интерфейс

Клиент фиксирует локальное pending-действие до запроса. После серверного
подтверждения удаляет только подтверждённые remote-строки из Drift и сохраняет
существующий owner/server/checksum marker в settings. Реактивная корзина пустеет
без ожидания физической очистки. `permanentComplete` устанавливается только при
физическом `complete`, а не при `accepted`.

Старое/повторное событие upsert или Restore не снимает marker. Принятие побеждает
запоздалый Restore того же объекта, но не может удалить объект другого аккаунта,
сервера либо заменённого checksum. Отложенные FK-события от уже принятого parent
отфильтровываются адресно; обычные нарушения FK продолжают вызывать ошибку.
Логический delete сохраняет marker до ACK sync; неизвестный сетевой исход не
подтверждается как успешная обработка.

Успех всех выбранных UUID показывает зелёное уведомление: «Корзина очищена.
Удаление файлов на сервере продолжается в фоне». Частичный отказ не показывает
полный успех. Во время ожидания серверного принятия можно уйти со страницы;
повторное нажатие блокируется, обновление Drift не зависит от жизни виджета.

Потеря ответа проверяется один раз через долговременный per-ID status. Если и
он недоступен, элементы остаются видимыми с uncertain intent; Restore ожидает
разрешения неопределённости. Отказ до принятия сохраняет корзину. Legacy backend
без явного `accepted` не даёт ложного зелёного успеха на queued-ответ.

## NAS, External и Samsung — разные операции

- Права и политика External Library не расширяются. Без существующего разрешения
  удаление External не принимается. Корни, mounts и файловая структура не меняются.
- Прежний tombstone препятствует повторному импорту того же пути; content checksum
  и aliases участвуют в существующем owner-scoped барьере повторного upload.
  Для старого External без заранее известного содержимого этот барьер по checksum
  появляется после безопасного hash. Неизвестное содержимое нельзя отождествить
  с другой копией только по имени.
- Новый путь очистки не вызывает `CleanupService` или MediaStore. Системное
  согласие Android и ранее настроенная синхронизация удаления остаются отдельными
  механизмами. Успех означает необратимое серверное решение, а не доказательство
  удаления оригинала из Samsung Gallery. Физически оставшийся local original
  сохраняется в БД устройства; существующий marker исключает его из объединённой
  ленты/повторного backup этому владельцу. Отдельные локальные альбомы могут его
  показывать.
- Код Magic Eraser Build 28, pointer handlers, версия APK, application ID,
  production-подпись, Motion/Live Photo autoplay и backend Big-LaMa не изменены.

## Проверка и границы подтверждения

Результаты конкретных автоматических прогонов и команды находятся в
[протоколе проверки](testing/2026-11-01-foto-build29-instant-trash-cleanup.md).
Используются только синтетические файлы, disposable PostgreSQL и тестовая SQLite.

Остаются отдельные реальные проверки HP/NFS/Redis restart и Samsung. Холодный
owner sync проверен; чужой уже открытый shared-space/library cache может получить
окончательное удаление позднее, при физической обработке. Это не возвращает
Restore и не даёт cold sync загрузить принятые объекты.

Уже выполняющийся media producer может оставить файл, который не успел
зарегистрировать в `asset_file`. Зарегистрированные производные защищены manifest
и блокировками; новые jobs для `Deleted` исключены. Эта работа не переписывает
компенсацию всех существующих media producers и не обещает отсутствие таких
незарегистрированных orphan-файлов при любом аварийном завершении.

Без отдельного решения не запускать production cleanup, миграции, deployment
или сборку APK. При откате исходников нельзя переводить принятые receipts обратно
в Trash: это уже необратимые пользовательские решения. До отката worker следует
проверить завершение или совместимое продолжение всех незавершённых receipts.
