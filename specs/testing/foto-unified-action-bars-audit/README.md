# Финальный аудит FOTO Unified Action Bars

Проверен коммит `010a7a6675d68dbfba5a457e6199cbb87516279a` в текущей ветке
`codex/foto-build38-unified-16`. Код приложения и утверждённый дизайн не изменены.
Добавлены два регрессионных тестовых файла и результаты аудита.
Backend, Docker, production, Adaptive Mosaic, анимация удаления, версия и подпись
не затронуты. APK не собирался.

**Результат:** геометрия панелей и доступность Upload/OCR прошли облачные проверки.
Новое требование прямого Google Lens в одно нажатие **не выполнено**: надёжный
документированный публичный контракт такого запуска не найден. Прежний Sharesheet
не считается выполнением этого требования.

## Фактическая геометрия

Размер Flutter viewport — **390×844 dp**, системные отступы сверху/снизу — по 24 dp,
светлая и тёмная темы FOTO, Google Sans, масштабы текста 100%, 150%, 200%.

В обычном просмотре при 100%:

- Видимая верхняя капсула: **44 dp**, координаты Y = 28…72.
- Область кнопок: **48 dp**, координаты Y = 26…74.
- Верхняя панель с вертикальными отступами: **52 dp**.
- Вместе с системным отступом 24 dp: **76 dp**, а не 136 dp.

`preferredSize.height = 112` задаёт свободную верхнюю границу ограничения Scaffold.
Внутренний `Column(mainAxisSize: min)` занимает фактическую высоту содержимого.
Обычная панель не резервирует 112 dp. Фото располагается в полном viewport
`Rect(0, 0, 390, 844)` благодаря `extendBody` / `extendBodyBehindAppBar`.

Новый тест использует настоящий `AssetViewer`, декодированный `FileImage`
1200×2400 и контроллер PhotoView. Нажатие на Y=84 — ниже фактической панели, но
внутри предполагаемой лишней области 76…136 — попадает в фотографию и скрывает
обе панели. Нажатие на прежнем месте скрытой панели возвращает их. При этом
прямоугольник, масштаб и позиция фото не меняются. Double-tap zoom и pan между
видимыми панелями тоже проверены.

| Масштаб текста | Верх обычного viewer, включая status inset | Верх Live Photo в общем альбоме, включая status inset | Низ, 3 локальных действия | Низ, 5 облачных действий |
| --- | ---: | ---: | ---: | ---: |
| 100% | 76 dp | 76 dp | 52 dp | 52 dp |
| 150% | 76 dp | 106 dp | 56 dp | 112 dp |
| 200% | 76 dp | 114 dp | 126 dp | 189 dp |

В общем альбоме сохранены Back / Live / Comments / Favorite / More; при крупном
шрифте дата переходит во вторую строку. Нижние действия переносятся целыми ячейками:
облачные при 150% — 3+2, при 200% — 2+2+1. Подписи не обрезаны и не разбиваются
на слова по строкам; области нажатия не меньше 48 dp. Корзина содержит только
восстановление и окончательное удаление. При 200% они размещаются в два ряда.

Нижняя капсула заканчивается на Y=820, перед системной областью навигации.
Верхние кнопки начинаются ниже status inset. Сами плавающие панели намеренно
рисуются поверх фотографии; её можно показать полностью, скрыв панели. Тесты
проверяют отсутствие лишней невидимой области перехвата жестов и сдвига фото,
а не утверждают, что видимые панели вообще не закрывают пиксели изображения.

**Исправление геометрии или дополнительное уплотнение не требуется.** Уменьшать
кнопки/шрифт ради высоты 52 dp при 200% было бы ухудшением доступности.

## Upload и OCR

Новый `viewer_menu_access_audit_test.dart`: **96 PASS** — 16 сценариев × 3 масштаба
× 2 темы. Проверяются реальные меню/ActionBuilder и вызов сервиса с выбранным ID,
появление/закрытие progress dialog, включение и выключение OCR.

Сценарии: локальное фото, локальное видео, локальный альбом, уже сохранённый в
облаке локальный файл, облачное фото/видео, Motion Photo, объединённый local/remote,
чужой доступный файл, альбом FOTO, local/remote readonly, local/remote locked,
корзина, отсутствие OCR-данных.

- Upload доступен через «Ещё» для несохранённых в облаке локальных файлов в
  разрешённом обычном просмотре и локальном альбоме. Запреты readonly/locked/trash
  сохранены; повторная загрузка облачного/уже сохранённого файла не добавлена.
- OCR доступен для облачных изображений с OCR-данными, включая доступный чужой
  файл, альбом и locked. В readonly он сохранён на нижней панели, поскольку меню
  «Ещё» там отсутствует. Для видео, корзины и отсутствующих OCR-данных не показан.
- Сервисы в widget-тестах подменены. Фактическая загрузка на production не выполнялась.

## Google Lens: ограничение и минимальный вариант

Проверена публичная документация Google/Android; HTTP 200 и хеши прочитанных
страниц сохранены в [lens-sources.json](lens-sources.json).

- [Передача изображения](https://developer.android.com/develop/ui/compose/sharing/send):
  `ACTION_SEND`, MIME-тип, `EXTRA_STREAM` с безопасным URI; `createChooser` открывает
  системный выбор приложения.
- [Общие Intent](https://developer.android.com/guide/components/intents-common):
  `ACTION_WEB_SEARCH` принимает текстовый `SearchManager.QUERY`, не изображение
  для гарантированного поиска Lens.
- [Intent API](https://developer.android.com/reference/android/content/Intent):
  `setPackage` ограничивает пакет получателя; наличие обработчика `ACTION_SEND`
  не гарантирует запуск функции Lens. `resolveActivity` не подтверждает семантику поиска.
- [Официальная инструкция Google Lens](https://support.google.com/websearch/answer/1325808?hl=en&co=GENIE.Platform%3DAndroid)
  описывает открытие Lens в Google/Chrome и выбор существующей фотографии.
- [Страница продукта](https://search.google/ways-to-search/lens/) не задаёт
  публичного контракта запуска поиска по URI из стороннего приложения.

В этих источниках не найден поддерживаемый контракт, гарантирующий **одно нажатие
в FOTO → поиск по текущему изображению в Lens**, без подтверждения/выбора приложения
на Android 13–16 и Samsung One UI. Это ограничение подтверждённых возможностей,
не доказательство отсутствия любого внутреннего механизма Google. Частные Activity,
недокументированные deep links и принудительная адресация приложения не добавлялись.

В `010a7a667` «Объектив» по-прежнему открывает поясняющий диалог, затем Sharesheet.
Текст диалога честно описывает передачу, но название кнопки само по себе может
создавать ожидание прямого запуска. **Этот путь не соответствует уточнённой приёмке**;
успех его прежних тестов означает сохранность fallback, а не успешный поиск Lens.

Минимальный практический сценарий для предложения пользователю:
**существующее «Отправить» → Google/Объектив в системном меню**, если установленное
приложение принимает изображения. Это два действия, без дополнительного поясняющего
диалога FOTO/подтверждения; подготовка файла может показывать прогресс. Такой сценарий
не равен прямой интеграции, не гарантирует наличие цели Google на каждом устройстве
и не объявляется принятым вместо нового требования. Если цели нет, официальный путь —
Google → Lens → выбор фото. Готовые панели и поведение Lens в этом аудите не менялись.

## Повторный запуск

Из корня репозитория, с готовым Flutter SDK и зависимостями проекта:

```bash
cd mobile
flutter analyze --no-pub
flutter test --no-pub --reporter expanded \
  --dart-define=FOTO_AUDIT_CAPTURE=/tmp/foto-action-bars-audit/viewer \
  --dart-define=FOTO_UNIFIED_CAPTURE=/tmp/foto-action-bars-audit/panels \
  test/presentation/widgets/asset_viewer/viewer_action_bars_audit_test.dart \
  test/presentation/widgets/asset_viewer/viewer_menu_access_audit_test.dart \
  test/presentation/widgets/asset_viewer/unified_action_bars_test.dart \
  test/presentation/widgets/bottom_sheet/unified_action_shell_test.dart \
  test/presentation/widgets/bottom_sheet/trash_action_bar_test.dart \
  test/presentation/widgets/asset_viewer/google_lens_viewer_test.dart \
  test/unit/presentation/actions/google_lens_action_test.dart \
  test/unit/presentation/actions/upload_action_test.dart
```

Хеши проверенных исходников: [source-manifest.json](source-manifest.json).
Хеши доказательств: [SHA256SUMS](SHA256SUMS).
Менялись только `viewer_action_bars_audit_test.dart`, `viewer_menu_access_audit_test.dart`
и этот каталог результатов. Повторный дизайн или исправление геометрии не вносились.
