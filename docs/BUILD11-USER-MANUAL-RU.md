# Gallery Build 11: удаление, корзина и восстановление

Эта инструкция описывает пользовательский интерфейс Build 11 и проверки после
установки. Она не подтверждает испытания на Samsung S23, iPhone или production
NAS: их результаты нужно записать отдельно. До одобрения владельцем сервера
production не обновляется и реальные оригиналы не удаляются.

Текущий Cloud application source: `89447178806ccc509ff0b52358b7491842041047`,
версия **5.7.3 (11)**. Старые артефакты `f26b4605…` заменяются новыми сборками:
они не содержат последние исправления backup и удаления локальных копий.
Неопубликованные HP-изменения не входят в этот релиз.

## Автоматическая загрузка фото и видео

1. Войдите своим существующим аккаунтом на прежний сервер Gallery. Не создавайте
   новые API keys или аккаунт ради включения backup.
2. В системных разрешениях Gallery разрешите доступ к фото и видео, которые
   должны загружаться. Для всех новых кадров нужен полный доступ: limited
   selection Android/iOS не даёт приложению читать будущие невыбранные снимки.
3. Откройте экран резервного копирования по значку облака. В карточке альбомов
   выберите папки/альбомы устройства: одно нажатие включает альбом, повторное
   исключает. Для приёмки используйте отдельный тестовый альбом.
4. Включите переключатель «Активировать». В «Параметры резервного копирования»
   проверьте network requirements для фото и видео; если cellular запрещён,
   дождитесь Wi-Fi. На Android проверьте «Выполнение фоновых задач», требование
   зарядки и задержку перед upload.
5. На Samsung разрешите уведомления Gallery и background работу в настройках
   батареи: Gallery → «Батарея» → «Без ограничений»; проверьте, что Gallery не
   внесена в список приложений глубокого сна. Названия One UI могут отличаться;
   экран backup показывает подсказки об уведомлениях и оптимизации батареи.
   Меняется настройка только Gallery, не VPN или другие приложения.
6. На iPhone разрешите Gallery доступ к Фото и «Обновление контента». iOS
   назначает время фонового запуска сама; после принудительного закрытия
   приложения откройте Gallery, чтобы backup мог продолжиться. Приложение не
   гарантирует мгновенную фоновую загрузку при screen lock, Low Power Mode или
   force-quit.
7. Создайте новое тестовое фото при открытой Gallery. На экране backup проверьте
   прогресс и «Просмотр подробностей»; в web подтвердите ровно один server asset
   и появление thumbnail/preview. Затем проверьте новое фото после сворачивания
   приложения, screen lock и offline→reconnect. Если загрузка задерживается,
   откройте Gallery и проверьте network/charging/OS ограничения и сообщение
   об ошибке; не очищайте данные приложения или tombstones.

Включённая синхронизация не должна возвращать в cloud Timeline объект,
отправленный вами в корзину. Для «Удалить из «Фото»» можно сохранить телефонную
копию и продолжать автоматический backup других кадров. Новое фото с новым
содержимым не считается ранее удалённым только из-за переиспользованного ОС ID.
Восстановление server asset не создаёт удалённый device file заново.

Клиентские Android/iOS scanners и фоновые расписания проверяются на реальном
телефоне отдельно. Успешный синтетический тест не подтверждает эти OS условия.

## Три разных действия

| Действие в Android/iOS | Сервер и NAS                                                                    | Локальная копия на телефоне                                                    |
| ---------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| «Удалить из «Фото»»    | Ваш объект перемещается в корзину, оригинал остаётся на месте                   | Сохраняется в системной медиатеке                                              |
| «Удалить с устройства» | Объект на сервере сохраняется                                                   | Приложение просит ОС удалить выбранную копию                                   |
| «Удалить везде»        | Ваш объект перемещается в корзину, оригинал остаётся до окончательного удаления | После подтверждения сервера приложение просит ОС удалить соответствующую копию |

Действия появляются только там, где они применимы: для объекта только на NAS
нет локальной копии, а для объекта только на устройстве нет серверного объекта,
который можно отправить в корзину. Чужие фотографии в общем альбоме не становятся
вашими: разрешение на просмотр не даёт права удалить чужой оригинал.

Браузер управляет серверными объектами. Он не может удалить фотографию из
Android MediaStore или iOS Photos; используйте мобильное приложение для операции
«Удалить с устройства». Удаление записи из альбома и удаление самой фотографии —
разные действия: выбирайте нужный пункт, не используйте удаление объекта вместо
исключения из альбома.

## Удалить одну или несколько фотографий

1. В ленте, альбоме, избранном или поиске выделите свои фотографии/видео.
2. Откройте меню выбранных объектов и выберите нужное действие из таблицы выше.
3. Для удаления локальной копии подтвердите системный запрос Android/iOS.
4. Прочитайте результат. Приложение отдельно сообщает об удалённых и оставшихся
   локальных копиях; отказ ОС не считается успехом. Неуспешный выбор сохраняется
   для проверки и повторной попытки.
5. Проверьте корзину. Объект не должен остаться в активной ленте, а NAS-оригинал
   при обычном перемещении в корзину должен сохраниться.

«Отменить» после серверного перемещения в корзину восстанавливает серверное
состояние. Это не восстановление файла, уже удалённого из системной медиатеки;
для «Удалить везде» приложение не обещает такую отмену. Если сервер не подтвердил
операцию из-за отсутствия сети или неизвестного результата запроса, приложение не
должно удалять единственную локальную копию.

Live Photo включает фотографию и связанный motion-компонент. Проверяйте их как
один пользовательский объект: в корзине/после восстановления не должны появиться
отдельные скрытые видео-дубликаты. Android Motion Photo и обычное видео также
проверяются отдельно; синтетический тест не заменяет испытание реального формата
на телефоне.

## Открыть корзину и восстановить

В мобильном приложении откройте «Библиотека» → «Корзина». В web выберите «Корзина»
в навигации. Корзина группируется по времени удаления; это не изменение даты
съёмки оригинала.

- Для одного или нескольких объектов выделите их и нажмите «Восстановить».
- Для всех объектов откройте меню корзины и нажмите «Восстановить все».
- Убедитесь, что восстановленные объекты вернулись на исходную дату в ленте,
  без дубликатов и «призрачных» плиток, сохранили метаданные и членство в альбомах
  там, где оно сохранялось сервером.

Восстановление не создаёт новый серверный объект и не записывает заново файл в
системную медиатеку телефона. Если локальная копия была намеренно удалена,
восстанавливается доступ к серверному оригиналу; сохранение новой копии на
устройство — отдельное явное действие.

Внешние offline index tombstones не являются пользовательской корзиной. В
частности, 291 ранее проверенная запись `active + deletedAt + isOffline` не
переводится в Trash, не показывается как подтверждённое пользовательское удаление
и не удаляется этой инструкцией.

## Управляемое хранилище

В Build 11 обычное окончательное удаление своих managed-объектов использует
штатный жизненный цикл Gallery и не требует каждый день вводить recoveryProof,
запрашивать администратора или запускать отдельный helper. Это не отменяет
проверку владельца, текущих корней хранения, целостности файла, общих ссылок и
защищённой операции с файловой системой.

В меню корзины доступен пункт «Разрешение окончательного удаления». Он показывает
состояние управляемого хранилища этого аккаунта и позволяет владельцу явно
запретить или снова разрешить удаление. Настройка managed не распространяется
на внешние библиотеки. Ошибка корня/монтирования или безопасной операции означает
остановку: не пытайтесь исправить её изменением прав всего NAS, отключением
проверки или прямым удалением записи из PostgreSQL.

Администратору по-прежнему нужны рабочие проверенные резервные копии и безопасная
процедура восстановления перед выпуском. Отсутствие ежедневной recovery-формы у
пользователя не доказывает восстановимость production-данных.

## Внешняя библиотека Synology: отдельный writable-режим

По умолчанию внешний оригинал защищён от физического удаления. Перемещение в
корзину и восстановление доступны без выдачи writable-разрешения; окончательное
удаление оригинала требует отдельной настройки этой библиотеки её владельцем.

1. Войдите именно в аккаунт владельца библиотеки. Не используйте аккаунт другого
   пользователя или администратора вместо его согласия.
2. Откройте корзину → меню → настройку окончательного удаления внешних библиотек.
   В web соответствующий раздел находится на странице корзины.
3. Выберите нужную библиотеку по имени и ID. Разрешение действует только для
   этой библиотеки и её текущих проверенных корней.
4. Прочитайте подтверждение и включите удаление только если эта библиотека
   намеренно настроена как writable и восстановление её данных проверено.
   Настроенный сервером срок корзины также может автоматически удалить допустимые
   trashed-оригиналы этой writable-библиотеки; разрешение не ограничивается одной
   текущей кнопкой «Удалить навсегда».
5. Сначала проведите приёмку на созданных для теста фото/видео, без семейных
   оригиналов. Для другой библиотеки и другого пользователя настройка отдельная.
6. При необходимости нажмите «Отозвать разрешение». После этого новые
   destructive-операции этой области должны быть запрещены.

Приложение не переводит read-only NFS mount в read-write и не обходит права NAS.
Если файловая система не разрешает безопасную операцию, результат остаётся
ошибкой. Изменение монтирования/идентичности корня требует новой проверки, а не
автоматического доверия строке пути. Не включайте разрешение для всех библиотек
одновременно ради устранения одной ошибки.

## Удалить навсегда и очистить корзину

1. Убедитесь, что выбранные объекты действительно в корзине и принадлежат вам.
2. Выделите нужные объекты → «Удалить навсегда» либо выберите «Очистить корзину».
3. Прочитайте и подтвердите разрушительное действие.
4. Дождитесь конечного результата: успешный HTTP-запрос или поставленная в очередь
   операция сами по себе не являются подтверждением физического удаления.
5. Если операция завершилась не полностью, проверьте сообщение по каждому
   объекту/области и повторите только неуспешные объекты после устранения причины.

Для смешанного выбора managed/external сначала проверяются все области. Если
для одной области нет разрешения, нельзя молча удалить другую часть выбора:
исправьте настройку нужной библиотеки или выберите только допустимые объекты.
После начала физической операции возможна отдельная ошибка файла/устройства;
приложение должно показать фактический результат и сохранить возможность
безопасной повторной попытки. Общий файл, на который ссылается другой объект или
пользователь, нельзя удалить как единоличный оригинал.

Если NAS/server удаление уже завершено, но Android/iOS отклонили удаление
телефонной копии, откройте меню корзины → **«Удалить оставшиеся копии на
устройстве»**. Прочитайте подтверждение и разрешите новый системный запрос.
Это удаляет только оставшиеся подтверждённые копии текущего аккаунта; повторного
удаления NAS/server и повторного создания server intent не происходит. При
повторном отказе ОС копия остаётся и результат показывает остаток. Если текущая
копия больше не совпадает с подтверждённым объектом, приложение её не угадывает
и не удаляет. Смена аккаунта прерывает подтверждение. Устаревший выбор с
недоступными ID требует нового выбора, а не молчаливого success.

Оставшаяся копия и server success — разные результаты. Не выбирайте повторное
«Очистить корзину» вместо device-only retry и не считайте исчезновение плитки
доказательством OS deletion. Старый неполный server receipt не даёт права
уничтожить телефонную копию без подтверждённого завершения.

После подтверждённого окончательного удаления повторный scan, backup или restart
не должен импортировать удалённый оригинал заново. Durable tombstones и receipts
сохраняются; их нельзя очищать вручную для «исправления синхронизации».

Автоматическое истечение корзины использует серверные Trash/retention-настройки
и тот же безопасный обработчик допустимых областей. Read-only внешняя библиотека
не получает право удаления от одного только срока хранения. Включение/изменение
production-retention — отдельное решение оператора; установка Build 11 не должна
самовольно менять установленную политику или возобновлять старые paused jobs.

## Обновить приложение без потери данных

Точные операторские команды, контрольные суммы и порядок установки приведены в
[Build 11 release runbook](BUILD11-RELEASE-RUNBOOK.md). Не используйте старые
артефакты Build 10 вместо перечисленного в нём единого source commit.

Android: новый APK должен иметь пакет `de.opennoodle.gallery`, versionCode 11 и
тот же production-сертификат, которым подписано установленное приложение. CI
debug-сертификат не подходит для обновления HP-signed версии. Устанавливайте
поверх существующего приложения; не удаляйте его и не очищайте данные. Саму
production-подпись выполняет оператор HP существующим ключом, без экспорта ключа
в GitHub или создания нового ключа.

iPhone: используйте готовый unsigned IPA из существующего GitHub Actions и
прежний SideStore/LocalDevVPN маршрут. IPA необходимо подписать в SideStore —
unsigned не означает «готов к прямой установке». Сохраните существующую app
identity, Apple ID/Personal Team, App Groups и Runner/ShareExtension/WidgetExtension.
Не выбирайте удаление extensions и не удаляйте прежнее приложение ради обновления.
Точное подготовленное IPA и extension-option берите из release handoff, который
проверяет реальные bundle IDs/entitlements; эта инструкция их не переопределяет.

Если новая версия не устанавливается поверх старой, остановитесь и проверьте
identity/signature, не используйте uninstall как обход. До physical-теста нельзя
заявлять сохранение данных или работоспособность extensions как PASS.

## Приёмка на Samsung S23, iPhone и web

Используйте отдельные disposable-фото и короткие видео с известными контрольными
хешами. Реальные семейные фотографии для этой проверки не нужны.

1. После холодного запуска откройте ленту: фото/видео доступны, Live Photo
   анимируется без предварительного открытия viewer. Проверьте прокрутку,
   возврат из viewer/фона, альбом и поддерживаемый поиск; обычное видео не должно
   автоматически воспроизводиться как Live Photo.
2. Для каждой из трёх операций из первой таблицы проверьте один объект и группу,
   включая OS permission denial. Сверьте ленту, серверную корзину и системную
   медиатеку отдельно.
3. Восстановите один объект и несколько: дата/метаданные/альбомы сохраняются,
   дубликатов нет, удалённая локальная копия автоматически не создаётся.
4. Проверьте окончательное удаление disposable-managed и отдельно writable
   external; затем read-only external и mixed выбор должны корректно отказать.
   Контрольный файл другого пользователя и общий оригинал остаются целыми.
5. Прервите сеть и повторите операцию; перезапустите приложение/сервер в рамках
   одобренного теста и выполните scan тестовой библиотеки. Запишите отсутствие
   unsafe replay, дублей и воскресших объектов.
6. Загрузите новое disposable-фото: thumbnail и preview появляются, web/Android
   viewer открывает фото, воспроизведение короткого видео работает. API и
   microservices должны оба работать; API-only режим запрещён.
7. Проверьте backup, поиск, лица, альбомы и ранее доступные Memories. Не запускайте
   массовый исторический анализ Memories и не меняйте модели ради этой приёмки.
8. Зафиксируйте статус PASS/FAIL/BLOCKED/NOT TESTED по каждому устройству и
   сценарию. Данные синтетических автоматических тестов приводятся отдельно.

Старые шесть подтверждённых FileDelete проверяются только по существующим sealed
intent и receipts; повторное удаление не допускается. Остальные 21 paused jobs
сохраняются. Ни инструкция пользователя, ни deploy не являются разрешением
глобально возобновить очередь или очистить Redis.
