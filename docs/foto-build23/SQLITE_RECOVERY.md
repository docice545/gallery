# FOTO Build 23 — восстановление SQLite

Версия Android: **5.7.3+23**, `versionCode=23`, package ID
`de.opennoodle.gallery`. Исходный коммит Build 22:
`a316a23f92c798da8927c34d1146a1d2de91b05a`. Ветка:
`codex/foto-build23-sqlite-one-tap-recovery`.

Production backend остаётся **5.7.3**. Серверные файлы, миграции, сервисы HP и
фотолента не входят в это исправление. Adaptive Timeline 2.0 — отдельная задача
после завершения P0, с отдельной веткой и релизом.

## Что делает одно нажатие

При повреждении локальной базы FOTO показывает «Требуется восстановление FOTO».
Само появление экрана не запускает исправление. Кнопка «Восстановить и открыть
FOTO» блокируется до завершения операции.

1. Общий для Flutter engines и isolates Android-владелец запрещает выдачу новых
   разрешений на открытие основной базы. Постоянная запись `selection` сохраняет
   этот запрет при перезапуске. Отдельный OS file lock исключает второй процесс.
2. Фоновый worker получает запрос отмены ещё до Bootstrap. Восстановление ждёт
   освобождения всех разрешений, максимум 30 секунд. Разрешение освобождается
   только после закрытия Drift, принадлежащего ему sqlite_async и update pool.
   Неуверенность в закрытии означает отказ, а не принудительную замену файлов.
3. В `Context.noBackupFilesDir/sqlite-recovery/attempt-*` сохраняются основной
   файл и существующие WAL/SHM. Каталог приватный, постоянный, не кеш, исключён
   из Android cloud backup; он сохраняется при обычном обновлении APK.
4. До копирования требуется свободное место: шесть размеров полного набора
   файлов плюс 64 MiB. SHA-256 источника до и после копирования должен совпадать
   с SHA-256 копии. Файлы и записи каталогов синхронизируются через `fsync`.
5. Существующий `diagnoseAndRepairSqliteSnapshot` работает только с отдельными
   копиями. Для этого сценария разрешён только
   `REINDEX idx_trashed_local_asset_album`; допускаются только точные сообщения
   о пропущенных строках этого индекса и неправильном числе его записей.
6. Проверяются заголовок и все кадры WAL, salts, rolling checksums, размер страниц,
   последняя подтверждённая транзакция и обе копии заголовка WAL-index в SHM.
   SHM подтверждает число кадров и commit checksum: корректной контрольной суммы
   усечённого префикса WAL недостаточно.
7. Кандидат проходит полный `integrity_check`, `foreign_key_check`, checkpoint
   и сравнение всех таблиц через `NOT INDEXED`. Сравниваются также скрытые rowid,
   `sqlite_sequence`, схема, `user_version` и `application_id`. Blob и text
   различаются при вычислении отпечатков. Виртуальные таблицы требуют ручного
   восстановления. Итоговый файл повторно открывается для независимой проверки.
8. Native-владелец сверяет SHA-256 кандидата, отсутствие непустого WAL/rollback
   journal, синхронизирует его каталог и атомарно записывает новый указатель
   вместе со снятием запрета. Исходные SQLite/WAL/SHM **остаются на месте**.
   Старая диагностическая функция по-прежнему возвращает
   **`promotionAllowed=false`**. Применение выполняет только отдельный coordinator
   после нажатия кнопки.
9. Выполняется обычный `openFoto`/Bootstrap: существующий Store, аккаунт, миграции
   и восстановление очереди Trash. Recovery не создаёт аккаунт, не обнуляет
   курсоры, не делает запросов удаления/загрузки и не подтверждает операции
   синхронизации. Обычная синхронизация становится доступной после проверок.

Сканирование таблиц и REINDEX выполняются в рабочем Dart isolate, чтобы экран
продолжал отображать ход операции. Фотографии не копируются и не удаляются.

## Прерывание и отказ

До атомарного переключения активным остаётся исходный набор файлов. После сбоя
процесса незавершённые попытки сохраняются; новый запуск видит постоянный запрет
и снова показывает экран восстановления. Кандидат, оставшийся после прерванного
REINDEX, никогда не подхватывается автоматически. Новая попытка создаёт отдельную
копию. Если переключение уже надёжно завершилось, следующий запуск использует
проверенный кандидат. Утрата/повреждение файла выбора поколения блокирует
открытие и применение: приложение не возвращается молча к старой базе с устаревшими
подтверждениями удаления. Все сохранённые поколения остаются доступны для экспорта.

Повреждённая страница таблицы, неизвестный индекс, FK-ошибка, изменение содержимого,
ошибка чтения/записи/fsync, нехватка места, неполный или неоднозначный WAL означают
отказ без сброса. Для базы с WAL-mode заголовком **отсутствующий/пустой WAL либо
отсутствующий/несогласованный SHM не позволяют доказать полноту транзакций**.
Автоматическое применение в этом случае запрещено, даже если SQLite показывает
`ok`. В частности, Build 23 не обещает автоматическое исправление любого
состояния Samsung только по тексту ошибки индекса.

Экран сообщает: «Автоматическое восстановление не удалось. Ваши исходные данные
сохранены». Кнопка экспорта открывает Android Storage Access Framework с выбором
локального места сохранения. ZIP записывается прямо в выбранный документ,
без промежуточного архива в кеше. Он содержит исходные SQLite/WAL/SHM, сохранённые
попытки и отчёты. Отмена/ошибка экспорта не удаляет внутренние файлы.

Обезличенный отчёт содержит перечислимую причину отказа, SHA-256 файлов, число
проверенных таблиц и результаты сравнения/FK/integrity. В отчёт не включаются
значения строк, пароли, токены, имена аккаунтов и пути к фотографиям. Сама
экспортируемая SQLite сохраняет пользовательские данные, включая имеющиеся
данные авторизации: архив остаётся у владельца и не отправляется приложением
разработчику или на сервер. При невозможности закрыть соединения экспорт также
не начинает чтение нестабильного источника.

Оригинал и резервные копии не удаляются автоматически после успеха. Указатель
не следует вручную возвращать на старую базу после возобновления синхронизации:
там уже могут отсутствовать новые изменения и подтверждения. Сохранённые файлы
дают возможность контролируемого отката/анализа, а не разрешение потерять новые
транзакции.

## Проверки и границы доказательства

Команды локальных проверок и CI:

```bash
cd mobile
flutter analyze --no-pub
flutter test --no-pub test/data/db test/pages/common/sqlite_recovery_page_test.dart \
  test/infrastructure/repositories test/domain/utils/background_sync_test.dart \
  test/domain/services test/services test/repositories
```

Перед тестами выполняется штатная генерация Drift/Dart/OpenAPI/переводов. Workflow
[FOTO Build 23 SQLite recovery](../../.github/workflows/foto-build23-sqlite-recovery.yml)
проверяет итоговый SHA: Flutter, Kotlin/Android compilation, native admission и
реальные файлы в Android emulator. Эмулятор выполняет обнаружение повреждения,
одно нажатие, открытие нового пула и сохранение ZIP через настоящий DocumentsUI;
CI отдельно проверяет архив, SHA-256, сохранённый WAL и отчёт. Итоговые статусы и ссылки на запуски приведены
в сообщении поставки; более ранний зелёный запуск не подтверждает новый SHA.

Регрессии используют настоящие SQLite-файлы. Повреждается листовая страница
именно `idx_trashed_local_asset_album`, получается точное сообщение
`wrong # of entries in index idx_trashed_local_asset_album`. Проверяются WAL-only
загрузки и удаления, подтверждённое удаление и курсор, повторная загрузка Store
из production Drift-схемы, сохранение currentUser/token/endpoint/deviceId, настоящие WAL-only записи
LocalAlbum/LocalAsset и журнал Trash; проверяются `getCandidates` и
`getPendingTrashOperations`, подтверждённое удаление остаётся исключённым из
загрузок и повторной обработки, повреждение
страницы данных, нехватка места, ошибки WAL и SHM, усечение целой транзакции,
отказ до/в процессе копирования, до/после REINDEX и перед применением. Отдельная
проверка SIGKILL завершает дочерний процесс внутри native SQLite comparator
реально исполняемого REINDEX. Проверка
закрытия пула убеждается, что после `Drift.close()` больше не остаются WAL/SHM,
которые SQLite удаляет только при закрытии последнего соединения.

Widget-тест проверяет русский текст, отсутствие автоматического запуска, одно
нажатие с настоящим восстановлением файлов и действие экспорта при отказе.
Kotlin-тесты проверяют запрет новых соединений, ожидание первого startup probe,
несколько владельцев, сохранение запрета после повторного открытия, атомарный
указатель, отказ при изменении кандидата/WAL/fsync и состав ZIP.

Проверки прерываний моделируют ошибки в контрольных точках и используют настоящий
SIGKILL дочернего процесса внутри REINDEX; они не являются испытанием физического отключения питания
Samsung. Гарантия атомарности опирается на Android/Linux rename и успешный fsync
файлов/каталогов при исправном хранилище. Аппаратную потерю данных вопреки fsync
программно исключить невозможно. Подписанный APK, совпадение сертификата и
обновление конкретного Samsung должны быть подтверждены на HP/телефоне; Cloud
не имеет ключа и не обозначает эти этапы как PASS.
